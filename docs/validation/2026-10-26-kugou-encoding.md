# 酷狗同曲编码误拒修复

日期：2026-10-26。环境：开发机 Linux x86_64、Electron 45、mpv 0.41；状态：编码误拒已复现并修正，用户本人歌单与登录态仍待真实复测。

## 反馈与实际复现

用户反馈酷狗所测曲目仅《不甘》能播放，其他曲目提示“平台返回的音频与所选曲目不一致”。截图包含带扩展名、歌手前缀和艺名/本名的文件名，没有完整取链错误上下文。进一步询问确认错误为 `track-mismatch`，不是一概资源不可用。

仅对用户已提供的公开歌曲进行匿名查询，没有登录或读取用户凭据，没有下载音频、保存签名 URL、原始响应或私人歌单截图：

- 《九万字》—黄诗扶：以搜索结果的无损 hash 请求标准 128kbps 时，返回标准 MP3 的 hash；返回的 hash/std_hash 都不同于无损 hash。旧逻辑会误拒。
- 同一原 hash 的资源详情明确返回该标准 MP3 为 `relate_goods` 中的编码。修复后通过身份校验；完整请求响应的权限仍未明确，后续试听请求明确 `is_full_audio=1`，因而按完整资源解析。这里只确认真实响应能解析，没有播放该真实音频。
- 匿名《一样的月光》和《不甘》另有无 URL 或试听权限边界未明确的响应。这不能代表用户 App 登录后的表现，也不将其统一归为无会员或下架。

《九万字》的编码转换是已确认的误拒路径；截图中所有歌曲在本人账号下是否恢复，仍需用户正式扫码验证，不能由这一次匿名查询宣称全部修复。

## 实现

1. 完整曲名比较兼容歌单文件名中的歌手前缀和艺名/本名格式差异。hash 已确认时不要求歌手显示文本逐字相同；不同曲名仍拒绝，转码试听的弱身份路径仍要求歌手匹配。
2. 初次身份校验失败时，使用同一 App 会话补查固定 `/v2/get_res_privilege/lite` 端点，按原 hash 精确匹配唯一资源；只接受该资源明确列出的音质 hash 和 Ogg 编码字段。返回顺序不同不会串行对应，相邻曲目或同名搜索不能补成证据。
3. 同时核对资源详情的完整曲名。权限继续由实际取链响应确认；编码关系中的 status/privilege 不直接充当完整播放授权，缺少试听边界仍拒绝。
4. 每次解析最多一次关系查询；关系只保留在本次后台调用，不进入 renderer、页面存储或跨账号缓存。新增等待点仍检查会话 generation 与解析序号。resolveTrack 内部请求预算调整为 45 秒，覆盖最多两次取链和一次关系查询的 10 秒网络超时；其余命令维持 30 秒。
5. 新端点仅在固定 transport 内使用，preload/IPC 没有新增通用请求、URL、Cookie 或 Token 接口。

## 验证

- 文档检查、严格类型检查与构建。
- 54 项单元测试，新增编码关系精确配对、别名格式、对应关系缺失、同名异曲、未确认试听权限、实际请求体与旧关系响应晚到。
- 5 项实际 mpv 集成测试，合成资源通过“原 hash → 另一编码”核验后实际解码，试听仍限制为明确授权的一秒，不以整曲资源长度放宽。
- 桌面 E2E 使用实际 Electron、mpv 和默认 PipeWire 输出，沿用 IPC、双平台匿名状态、会话队列及退出清理验证；不自动扫码、不截图私人数据。
